# Журнал измерений

Сырые результаты проверок, на которых построены выводы. Машина: Windows 10/11, Ethernet 1 Гбит/с, провайдер РФ, октябрь 2026. Клиент Roblox `0.744.0.7441080`.

---

## 1. Логи: ассеты не качаются

Сессия 15 минут, до фикса:

```
ответов HTTP ......... 54
успешных ............. 4
зависаний (net>=50 c)  47-49
ошибок ассетов ....... 368
успешных ответов CDN .. 0
```

Оговорка по «ошибкам ассетов»: счётчик `AssetResolutionWorkflow` включает и модерированные
ассеты (`AssetDelivery403`, «Asset has not been reviewed»), которые к сети отношения не имеют.
В последующих сессиях таких строк было 58 при полностью здоровой сети, поэтому в скриптах
этот счётчик теперь отделён от сетевых ошибок. Основной признак проблемы — `net:>=50 c`, а не
общее число строк `AssetResolutionWorkflow`.

Типовая строка:

```
HttpResponse(#162 0x2012dc738f8) time:60015.7ms (net:59999.4ms timeInRetryQueue:0.0ms)
error:5 message:HttpError: Timedout
url:{ "https://fts.rbxcdn.com/v2/sc3/76170d45...?encoding=zstd&version=1&__token__=...&Expires=1792981310" }
ip:3.164.206.34 external:0 numberOfTimesRetried:0
```

Вывод: зависает не сеть в целом (другие хосты отвечают за 250 мс), а именно загрузка с CDN, ровно по 60 000 мс на запрос, 0 байт.

## 8. Телепорт между серверами (отдельная проблема)

Сессия 24.10, до каких-либо изменений в zapret. Все четыре телепорта шли **напрямую на публичный IP** (без UDMUX) и все четыре не дошли до репликации:

| Время (UTC) | Сервер | Порт | Результат |
|---|---|---|---|
| 21:33:12 | 18.199.177.144 | 53233 | `AckTimeout`, `ID_CONNECTION_LOST` |
| 21:33:52 | 35.159.10.189 | 58158 | нет `Server RobloxGitHash`, клиент вышел |
| 21:38:50 | 18.197.46.202 | 51696 | `AckTimeout`, `ID_CONNECTION_LOST` |
| 22:27:19 | 63.179.58.66 | 63135 | `AckTimeout`, `ID_CONNECTION_LOST` |

Типовая последовательность:

```
Connection accepted from 63.179.58.66|63135
Replicator created for player 63.179.58.66|63135
AckTimeout: Last Packet received time: 20003 ms
Connection lost - Cannot contact server/client
```

При этом обычные входы в ту же сессию через `UDMUX 128.116.x` работали и доходили до `Server RobloxGitHash`.

Проверки с той же машины:

| Проверка | Результат |
|---|---|
| `ping` до 18.199.177.144 / 18.197.46.202 / 63.179.58.66 / 35.159.10.189 | 4/4, 41–53 мс |
| `ping -f -l 1472` до тех же адресов | проходит (MTU не при чём) |
| Правила файрвола RobloxUnlocker | только `UDP 443`, игровые порты не затрагивают |
| `ipset-all.txt` в zapret | заглушка `203.0.113.113/32`, то есть desync к игровому трафику не применялся |

Вывод: рукопожатие проходит, дальше провайдер перестаёт пропускать UDP. Это не QUIC, не DNS, не MTU и не правила RobloxUnlocker.

### После включения UDP-desync

В `ipset-all.txt` добавлены все IPv4-префиксы AWS `eu-central-1` (454 шт.), `winws` перезапущен. Следующие два телепорта (23:09 и 23:11 UTC) прошли:

```
SessionTransitionFSM] Teleported.
Joining game ... at 10.9.1.220
UDMUX Address = 128.116.44.33, Port = 56838
Server RobloxGitHash: ...
AckTimeout 1: 0
```

Честная оговорка: в этих двух случаях Roblox выдал UDMUX-серверы, а не прямой публичный адрес, поэтому нельзя утверждать, что сработал именно desync, а не выбор сервера. Надёжно проблему решает VPN; desync — экспериментальный вариант, который нужно проверять на своём провайдере.
